## 1. What this is

A camera-first inventory system for the SAC robotics club room. Members point a phone at a
component → it is identified (QR label first, AI vision second) → they see its rack, bin, specs
and free stock → one tap logs a checkout in their name with a due date. Admins approve members,
edit the catalogue, and see who has what.

- **Scale:** ~40 users max, ~28 catalogue rows today. Nothing here needs to scale further.
- **Form factor:** installable PWA (phone) + web dashboard (room computer).
- **Origin:** generated by [Lovable](https://lovable.dev), then hand-iterated (90 commits).

## 3. The one thing you must internalise

> **The business logic lives in PostgreSQL, not in TypeScript.**

`src/lib/*.functions.ts` is a thin, validated RPC shim. The authoritative invariants — stock
decrement, over-borrow prevention, extension limits, damage accounting, permission checks —
are `SECURITY DEFINER` PL/pgSQL functions in `supabase/migrations/`.

If you read only the React and TypeScript, you will misunderstand this system.
**Read the SQL first.**

## 4. Architecture

```
┌──────────────────────────────────────────────────┐
│  L1  Presentation      src/routes/ + components/ │  React, browser
├──────────────────────────────────────────────────┤
│  L2  Client data       src/lib/queries.ts        │  TanStack Query cache
├──────────────────────────────────────────────────┤
│  L3  RPC boundary      src/lib/*.functions.ts    │  Zod + middleware
│      ══════ NETWORK / TRUST BOUNDARY ══════      │
├──────────────────────────────────────────────────┤
│  L4  Server services   src/lib/*.server.ts       │  node:crypto, service role
├──────────────────────────────────────────────────┤
│  L5  Data + RULES      supabase/migrations/*.sql │  ★ RLS + SECURITY DEFINER
└──────────────────────────────────────────────────┘
```

**Layer boundaries are enforced by file naming, not tooling:**
- `*.functions.ts` → ships to **both** bundles; everything in it is network-callable
- `*.server.ts` → server only; safe place for `node:crypto` and the service-role key

## 6. Database

### Tables (7, all with RLS enabled ✅)

```
auth.users ──1:1──▶ profiles          full_name, email, roll_number, phone,
     │                                approval_status ('pending'|'approved'|'rejected'),
     │                                approved_at, approved_by
     ├──1:N──▶ user_roles             role: app_role enum ('admin'|'member')
     └──1:N──▶ borrow_records ──N:1──▶ components ──N:1──▶ racks
                 quantity                name, category      code (UNIQUE)
                 borrowed_at             specs               name
                 due_at                  quantity_total      description
                 returned_at             quantity_available  location_note
                 note                    rack_id
                 extended_count          bin_label
                 damage_reported         qr_code (UNIQUE)
                 damage_note             keywords text[]
                 reminded_soon_at        borrowable
                 reminded_overdue_at

notifications   user_id, borrow_record_id, kind, title, body, read_at
                kind ∈ due_soon | overdue | approved | rejected
unknown_scans   user_id, guessed_name, guessed_category, notes, resolved_at
```

### Functions (all `SECURITY DEFINER SET search_path = public` ✅)

| Function | Purpose | Key detail |
|---|---|---|
| `borrow_component(uuid,int,int,text)` | Atomic checkout | `SELECT … FOR UPDATE` row lock; checks `is_approved`, `borrowable`, stock |
| `return_component(uuid,bool,text)` | Return + damage | Idempotent (early RETURN if already returned). Damaged ⇒ `quantity_total -= qty`; else `quantity_available += qty` |
| `extend_borrow(uuid,int)` | Push due date | Max 3 extensions for non-admins; resets both `reminded_*` flags |
| `generate_return_reminders()` | Reminder sweep | ⚠️ **NEVER SCHEDULED — see §9** |
| `has_role(uuid,app_role)` | Role check | STABLE. Used by `getMe` and several RLS policies |
| `is_approved(uuid)` | Approval check | Called inside `borrow_component` |
| `handle_new_user()` | Signup trigger | Creates `profiles` row (pending) + `user_roles` row (member) |
| `guard_profile_approval()` | BEFORE UPDATE trigger | ⚠️ **Silently reverts** approval fields when `auth.uid() = NEW.id` |

### Migration discipline

10 migrations. **Four of them exist solely to `REVOKE` default grants** from `PUBLIC`/`anon`.
Postgres grants `EXECUTE` to `PUBLIC` on new functions by default — this codebase correctly
clamps that every time. Preserve that habit.

Seed data: 6 racks (R1–R6), 28 components, QR codes `SAC-C-0001`…`SAC-C-0028`.

## 7. The two auth systems (do not confuse them)

```
SYSTEM 1 — MEMBERS                       SYSTEM 2 — ADMIN PANEL
Supabase Auth (email/pw + Google)        SAC_ADMIN_PASSWORD (one shared secret)
  ↓                                        ↓
JWT in localStorage (auto-refresh)       sha256 ×2 → timingSafeEqual
  ↓                                        ↓
attachSupabaseAuth adds Bearer           h3 sealed cookie "sac-admin"
  ↓                                        { unlocked:true }, httpOnly, secure,
requireSupabaseAuth → getClaims()          sameSite lax, 8h
  ↓                                        ↓
per-request client                       isAdminUnlocked() — hand-checked in 12 handlers
  ↓                                        ↓
RLS evaluates auth.uid()  ✅             supabaseAdmin — ⚠️ NO RLS
```

**They do not interact.** `/admin` is **not** inside `_authenticated`. A user can hold an
unlocked admin session while signed out entirely.

⚠️ `isAdmin` (from `has_role`, System 1, gates `/dashboard`) is **unrelated** to the admin
session (System 2, gates `/admin`). A user can be `isAdmin: true` and still see the unlock screen.

### Three authorization mechanisms

1. `user_roles` + `has_role()` → `isAdmin` → hides `/dashboard` nav; **RLS enforces the data**
2. `profiles.approval_status` + `is_approved()` → `AppShell` gate (UX) + `borrow_component` (enforcement)
3. Admin session cookie → `/admin`

⚠️ `/dashboard`'s admin check is client-side only (`dashboard.tsx:72`). This is **not** a hole —
`getBorrowLog({scope:"all"})` is filtered by the RLS policy `"borrow read own or admin"`.
Correct defence in depth; easy to misread as a vulnerability.

## 8. Request lifecycle (the borrow path)

```
ComponentDetail onSubmit
  └─ useMutation → useServerFn(borrowComponent)
      └─ attachSupabaseAuth.client()   → Authorization: Bearer <jwt>
          └─ POST /_serverFn/…
════════════ NETWORK / TRUST BOUNDARY ════════════
              ├─ errorMiddleware
              ├─ csrfMiddleware  (handlerType === "serverFn")
              ├─ inputValidator  → zod.parse (uuid, 1..100, 1..90, ≤200 chars)
              ├─ requireSupabaseAuth
              │    header ✓ → "Bearer " ✓ → 3 dot-segments ✓
              │    → createClient(URL, ANON, { headers:{ Authorization } })
              │    → getClaims(token) → claims.sub
              │    → context = { supabase, userId, claims }
              └─ handler → supabase.rpc("borrow_component", …)
════════════════ POSTGRES ════════════════
                   auth.uid() ✓
                   is_approved(uid) ✓
                   SELECT quantity_available, borrowable FOR UPDATE   🔒 ROW LOCK
                   borrowable ✓  avail >= qty ✓
                   UPDATE components SET quantity_available -= qty
                   INSERT INTO borrow_records (…, due_at = now() + N days)
                   COMMIT                                             🔓
              ← { recordId }
  └─ onSuccess: toast + invalidateQueries(["inventory"]) + (["borrows"])
```

**Why the row lock matters:** two members tapping Borrow on the last servo simultaneously.
Without `FOR UPDATE` both read `avail = 1`, both decrement, stock goes to `-1`. With it, the
second transaction blocks, re-reads `avail = 0`, and raises `Only 0 available`.
✅ This is the best-engineered part of the codebase.

### What is done well (don't "fix" these)

- RLS on all 7 tables; `SECURITY DEFINER` + explicit `SET search_path` on all 8 functions
- Systematic `REVOKE` migrations
- `FOR UPDATE` row locking in the borrow/return/extend trio
- **AI hallucination firewall** — `identify.functions.ts:122-124` whitelists the model's returned
  id against ids read from the DB in the same request. A fabricated uuid can never enter the app.
- `guard_profile_approval` trigger — members cannot self-approve
- CSRF middleware explicitly re-registered after `start.ts` opted out
- `safePath()` blocks `//evil.com` open-redirect (`auth.tsx:33-36`)
- `bunfig.toml` 24-hour `minimumReleaseAge` supply-chain guard
- Defensive AI JSON parsing: `JSON.parse` → regex salvage → `{}`; never throws on bad output
- Every AI string field is `.slice()`-clamped

### Vision provider chain (`src/lib/ai-vision.server.ts`)

Providers are resolved from env **at call time** and tried in order; one whose key is
unset is skipped rather than failing. All three speak OpenAI `chat/completions`, so the
request body is identical and switching is a URL + header swap.

| Order | Provider | Endpoint | Auth header |
|---|---|---|---|
| 1 | Gemini | `generativelanguage.googleapis.com/v1beta/openai/chat/completions` | `Authorization: Bearer` |
| 2 | generic fallback | `AI_FALLBACK_URL` | `Authorization: Bearer` |
| 3 | Lovable | `ai.gateway.lovable.dev/v1/chat/completions` | `Lovable-API-Key` |

Failover on: non-2xx, `200` with empty content, network error, or a 30s timeout.
The surfaced error reflects the **worst** failure seen (`rate_limited` < `out_of_credits`
< `unavailable`), so "everything is rate limited" isn't masked by one 500.
Every attempt logs `[vision] <provider> failed <status>` before moving on.

⚠️ Fallback **model ids live in env, not source** — free model names churn, and a rotated
name shouldn't need a redeploy.

## 11. Gotchas that will bite you

1. **`start.ts` existing disables Start's automatic CSRF middleware.** It is re-added manually.
   Don't delete those lines.
2. **`error-capture.ts` must be the first import in `server.ts`** — it patches `console.error`
   before anything can throw.
3. **Supabase clients are lazy `Proxy` singletons.** A missing env var throws at first
   *property access*, not at import. Debuggers show a `Proxy`, not a client.
4. **`await import("@/integrations/supabase/client.server")` inside handlers only.** A top-level
   import from a `*.functions.ts` file risks the service-role key reaching the browser bundle.
5. **TS ↔ SQL parameter names are coupled invisibly.** Renaming `_component_id` breaks the
   `.rpc()` call at runtime; the compiler cannot see it. Regenerate `types.ts` after every
   migration.
6. **Adding a component column touches 5 places:** migration → `types.ts` → the `Component` type
   in `inventory.functions.ts` → every `.select()` string (4 of them) → `ComponentDialog` draft.
7. **`BarcodeDetector` is Chromium/Android only.** Safari and Firefox users always fall through
   to the AI path — factor that into cost estimates.
8. **Never force-push.** `AGENTS.md`: rewriting pushed history breaks Lovable's sync and can
   destroy project history.
9. **`routeTree.gen.ts` and `types.ts` are generated.** So are all five files in
   `integrations/`. Edits get overwritten.
10. **`guard_profile_approval` silently reverts** — an UPDATE to your own approval fields
    appears to succeed and does nothing.

## 12. Glossary

| Term | Meaning |
|---|---|
| **approval_status** | `pending`/`approved`/`rejected` on `profiles`. Blocks borrowing. Protected by `guard_profile_approval`. |
| **BarcodeDetector** | Browser-native QR API. ⚠️ Chromium/Android only. |
| **bin_label** | Drawer/box within a rack, e.g. `B2-05`, `BOX-RES`. |
| **borrowable** | `false` for shared bin boxes (resistors, ICs, screws) — take what you need, no checkout. |
| **h3** | The HTTP layer under Nitro. Swallows in-handler throws into `{"unhandled":true,"message":"HTTPError"}` — the reason `error-capture.ts` and `normalizeCatastrophicSsrResponse` exist. |
| **hallucination firewall** | `known.has(rawId) ? rawId : null` — the AI may guess *what* a part is but never *which DB row*. |
| **`mono-tag`** | Custom Tailwind utility: uppercase monospace micro-label. |
| **`panel`** | Custom Tailwind utility: surface + border + shadow card. |
| **rack** | Physical shelf unit `R1`–`R6` with `code`, `name`, `location_note`. |
| **RLS** | Row Level Security — Postgres per-row policies. **The** authorization boundary. |
| **`SECURITY DEFINER`** | Runs with the function owner's privileges. Always paired here with `SET search_path = public`. |
| **server function** | `createServerFn(...)` RPC — the trust boundary. |
| **service role** | The Supabase key that **bypasses RLS**. Only `client.server.ts`, only admin paths. |
| **unknown_scans** | Queue of parts the camera saw but the catalogue lacks; triaged in `CataloguePanel`. |
